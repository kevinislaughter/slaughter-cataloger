# Slaughter Cataloger 3 — working notes

Rebuild of Slaughter Cataloger (Beta 2.7, now `legacy/beta-2.7/`) agreed 2026-10-08. Workflow stays 1 Library → 2 Issues → 3 Contents → 4 Compiler.

## Public repository rule
Everything in this repository is generic and invented: sample data and test fixtures come from `tools/make-sample.js` and `tools/make-issue-fixture.js`; example names are placeholders (John Q. Public, Jane Doe, Richard Roe, Anytown, The Example Gazette); no title, credit, text or other detail from anyone's real catalog appears in code, tests, comments, docs, screenshots or the legacy apps. Real material is used only in private acceptance runs, from a path outside the repository. Before publishing, `SC_PRIVATE_TERMS=<list kept outside the repo> sh run-tests.sh` runs `tools/scan-terms.js` over every text file (images are listed for checking by eye).

## Architecture (do not drift from this)
- **One schema** (`js/core/schema.js`): every CSV column defined once. Forms, tables, CSV read/write, Speculative/N/A lists and outputs derive from it. Add a field there, nowhere else.
- **One store** (`js/core/store.js`): the only copy of the data. Records are frozen; change = `store.put/remove`, grouped with `store.batch`. Undo/redo and dirty-file tracking live there. Views never keep their own copies.
  Changed files by **revision**: every undo step gives each file it touches a new revision number (never reused); undo/redo restore the file's previous/next number. A file is changed when its revision differs from the one recorded at its last save, or it was marked changed (on load, or restored) and not saved since. Undoing past a save then making a different edit can never look saved (review B-01). A save passes `store.revisions()` taken when it started, so edits made while it writes stay changed. Listeners get `(version, event)`; `event.changed` = `[kind, id]` pairs (used by the journal).
- **Pure logic in core** (`js/core/numbering.js`, `js/core/toc.js`): next-issue numbering and dates, cadence, short names, gaps in a run; contents nesting/reordering and pasted-line parsing. No DOM; unit-tested in Node.
- **One view model for every output** (`js/core/catalog.js`): resolves inheritance and field states once (`issueView`, `titleView`, `contentView`), and writes numbering, dates, physical facts, labels and the typeset entry as "parts" (strings and `{text, spec}`), rendered by `toText`/`toHTML` with speculative values as `[1872?]`. The editors' typeset entry (`IssueEntry`) uses the same `entry()`. `build(store, {titleIDs, issueIDs, nested, limit, date})` → titles (alphabetical, ignoring a leading article; titles without a record last) with issues and contents.
- **Names** (`js/core/names.js`): credits split on `;`, ` & ` and a slash between names (not between digits); match key ignores case, spacing, punctuation and accents; `suggestHeading` (surname first; lower-case particles after the forenames, capitalized ones with the surname; suffixes; roles like "translated by" / ", editor", honorifics and bracketed notes set aside; bodies, single words and initialisms left as given); `index(state)` (forms, heading of each key, entries in word-by-word filing order); `suggestGroups` (same surname, agreeing initials and forenames incl. Wm./Geo./… abbreviations, initialisms like S.E.P. joining the name they spell; ambiguous short forms left out; tie → more shared initials). Pure; `tools/test-names.js`.
- **Outputs** (`js/core/outputs.js`): pure builders on the view model — `checklist` (html/md/txt; styles plain, bibliographic, technical), `catalog` (standalone HTML), `wordpress` (blocks), `proofing` (print HTML), `ris`, `bibtex`; `filename()` = `SCATOUT_<SLUG>[_<TITLEID> when one title]_<TYPE>_<YYYYMMDD>.<ext>`. All user values escaped; 2.7 attribution line kept.
- **Files are the archive** (`js/core/records.js`): read 2.0/3.0 CSVs, migrate, validate, write 3.0. Each record keeps `_src` (its file) and `entryOrder`; saves write back to the same file, keeping that file's BOM/line-ending/quoting style. Unknown columns are preserved. A file's fingerprint (`records.hashText`, used to tell that a file changed on disk or since it was saved) is 128 bits from two seeded cyrb53-style passes plus the length (`c2:` prefix; review 2, R-04); where both texts are at hand, saving compares the texts themselves.
  **Never drop or change a value** (review B-03/B-04/M-02/M-03/M-05): `csv.parse` throws (with the line) on an unclosed quote or text after a closing quote; `readFile` refuses a file with a heading used twice, a column and its alias both present, values under a blank heading, or a row longer than the header. A row with fewer values than the header is refused too (a missing comma shifts values). The file's tool and library slug are the ones most of its rows name. Rows it cannot take in — another tool, another library slug, a repeated TitleID/IssueID/ContentID/AuthorityID, no TitleID — are **set aside verbatim** (`files[name].setAside = [{row, reason, cells}]`) and written back at the end of the file on every save; the Library page lists them. Issues without an IssueID (but with a TitleID) get one minted, like contents. A Parent ContentID that is missing, the item itself, in another issue, listed after the item, or on a loop is not used (item at top level) but kept in `parentKept` and written back; re-nesting in the grid clears it. Parent Item text only links to an earlier item. Yes/No columns read Yes/Y/True/1/X/✓ as yes; a value written any other way is kept in `boolRaw` and written back unless the field changes (unrecognised values are reported). Names in Overridden Fields that are not inheritable fields are kept (`overridesKept`). An issue whose title is not loaded keeps every value and its Overridden Fields exactly as read (`finishIssue` compares with the title only when there is one), so saving it changes neither; the issue form shows such values as its own. Backup files are `…_BACKUP_<digit>…` (a slug may be BACKUP). On a reconnect, files already loaded win over copies that appear (`buildLibrary` `opts.pinned`); the copy is reported as a warning.
- **Session** (`js/app/session.js`): folder open/save (File System Access), browser working copy, reconnect, download fallback. UI never touches files.
  - Files read but not loaded (unreadable, another library, Beta 2, copies) are kept as `store.unloaded` (name → why; persisted with the snapshot, recomputed on every open/load/sync). `store.blocked(name)` refuses a new record whose file would take such a name (the four `fileForNew` call sites say why and add nothing), and `storage.writeFiles` never writes a file new to the app (`mustNotExist`) over one already in the folder (`occupied`) — independent check round 2, item 1. An empty file is not "occupied" and is not counted as unloaded (a first write that failed leaves one; `writeFiles` also removes it where it can) — round 3, A. Names compare without case.
  - Working copy = IndexedDB `kv.session` (snapshot + `seq` + `gen` + mode + folder handle + `diskSeen`) and a `journal` store: every store event appends an entry at once (changed records, all file metadata, dirty list, `gen`); a snapshot replaces the journal after 4 s quiet or 200 entries (one transaction). Every store `load` starts a new `gen` (time-based, unique) that needs its own snapshot; until that is stored the red notice stays (`needsSnapshot`), failed snapshots retry every 5 s. Restore = snapshot + replay of entries of the snapshot's `gen` only (others reported as not restorable, never mixed in); `seq` continues from the highest number in storage. A journal entry that fails sets `needsSnapshot` (the notice stays until a snapshot is stored) and its number goes into `missed`, carried by later entries; restore reports any missing number (named in `missed`, or absent between the snapshot and the last entry replayed) as "could not be restored" (round 2, item 4). Failures are also counted in localStorage (`storage.unstored`, cleared by a stored snapshot), for when nothing later reached IndexedDB to name them (round 3, C) — reported on restore even when no snapshot of the library was ever stored (round 4). Writes are serialized; failures set `ui.storageProblem` (B-06). `flush()` runs a due compaction and resolves when written.
  - One tab at a time (B-07): Web Locks where available (`storage.takeLock`, retried for 2 s because a reload's new page can start before the old one lets go), else a liveness note in localStorage (`slaughter-cataloger-3-owner`, every 2 s, removed on pagehide; fresher than 6 s = taken). Without Web Locks a fresh note from another tab is watched for 2.6 s first: a note that is not renewed was left by a crashed tab, and is taken over. Either way `kv.owner` = this tab's id **fences every IndexedDB write** (checked inside the write's transaction; a stale tab gets `NotOwner` → `access: 'lost'`), and saves check it before writing. Second tab: "Already open in another tab" → `takeOver()`.
  - Saves run one at a time (`save()` queues behind a running save; Ctrl+S included), so an older version of a file never lands on a newer one. The folder handle lives in the same record as the snapshot; a reconnect to a folder holding another library slug reads and writes nothing (`ui.wrongFolder`) until **Choose folder** (`chooseFolder`, keeps unsaved work).
  - Reconnect (`syncFromFolder`) compares the folder with `st.files` and `diskSeen` (every CSV seen at the last read): new files are read, clean changed files re-read, dirty files keep the user's version (a dirty file whose disk text equals what the app would write counts as saved — an interrupted save), files gone from the folder keep their records with `missing: true` (never written again until back, or removed via `forgetFile` with a confirm), files that no longer parse keep their records with `unreadable` (B-02, M-01). Undo history is kept when nothing changed.
  - Save writes each file on its own (`storage.writeFiles` → `{saved, already, backups, conflicts:[{name, backup}], missing, occupied, failed, stopped, notWritten}`); ownership (`stillOwner`) is checked before each file and again just before each write is swapped in (else `abort()`), so a tab taken over mid-save writes nothing more (round 2, item 2). Folder writes run under a second Web Lock (`withSaveLock`): a tab taken over in the instant between its last check and the swap still holds it, so the new tab's save waits, then finds the file changed on disk and backs it up rather than being overwritten after it (round 3; without Web Locks this instant remains). When a tab loses the library, every write it has in progress (backups too) is aborted at once (`storage` `inflight`), so the new tab's save never waits on a doomed write (round 4). An empty file is never backed up; only written files are marked saved; a file already on disk exactly as wanted is not rewritten and not reported as a conflict; a backup is always written before an overwrite (M-04, m-01).
  - Files mode (no folder access): Save downloads; files stay changed until **I've replaced the files** (`confirmDownload`, marks saved at the revisions downloaded) (B-05).
  - `whenReady()` resolves when start-up (restore + folder check) is done; tests wait on it.
- **UI** (`js/ui/*`): Preact + htm, vendored in `js/vendor/` (no CDN, no build step). Views render from (store, route). Route = `#/panel/titleID/issueID`, plus an optional ContentID segment on contents (`#/contents/<tid>/<iid>/<cid>`, open at that item) and a query on search only (`#/search?q=…&kind=…&order=catalog&from=<tid>`). `navigate` never carries an item or a query over to another visit. htm does not decode character references (`&lt;` shows as typed): write the character itself, or `${'<…>'}` where `<` would open a tag; whitespace holding a newline between text and `${}` is dropped.

## 3.0 data decisions
- **Name authorities**: one file per library, `SCAT_<SLUG>_AUTHORITIES.csv` (tool "Authorities"; kind `authority`; `state.authorities`), AuthorityID `AU-` + 6 chars. Columns are a superset of the Beta 2 `AUTHORITY_<TitleID>.csv` lists (Authorized Form ← AuthorizedForm, Variant Forms ← VariantForms joined with " | ", Type, Roles, Honorifics, Notes, Status "Needs review"/"Confirmed"; plus Dates, See Also, Sources). Count is not stored (derived). A heading matches its listed forms, its own form and that form in direct order. Contents are never changed by headings. `R.mapOfKind` is the one place that maps a kind to its Map.
- **The app reads schema 3.0 only.** Beta 2 (2.0) files are converted once with `tools/convert-to-3.js`; the app lists them as "Beta 2 format, not loaded" and never touches them. `readFile(..., {legacy:true})` is used only by the converter and tests. Versions are normalized ("3" = "3.0", spreadsheets drop the ".0").
- Converter: record-level merge of copies (files sharing IDs; per title for issues). Newest copy of a list is authoritative; records only in older copies go to `_left-out/` verbatim and into the report. Contents merge per issue (newest file holding that issue wins; older-only issues kept). Output: one Titles file per library, one Issues + one Contents file per title, canonical names `SCAT_<SLUG>_TITLES.csv`, `SCAT_<SLUG>_<TITLEID>_ISSUES.csv`, `SCAT_<SLUG>_<TITLEID>_CONTENTS.csv`, plus `CONVERSION-REPORT.md`. Verified by re-reading with the 3.0-only reader.
- Title edits mark issues files changed only when an inherited field, Title Code or First Year changes. A library change marks only the files whose rows carry what changed (`store.libraryFiles`): the slug every file with rows, the name Titles and Issues files, the note the Titles file; another file with no rows (DF-19) is not marked, the Titles file always is, since the library's values belong there and Save then refuses an empty one and says why (A2 minor; before, every file was marked).
- Changing a TitleID is a deliberate migration done with `tools/change-titleid.js <folder> OLD NEW --out <dir> [--partial-copy]` (run with `TZ=America/New_York` for the date): IssueIDs/ContentIDs keep their codes with the new prefix, files renamed, a dated sentence is added to General Notes, leftover text mentions are listed. Done once on a real library (2026-10-08). Since A3 batch 1 (2026-10-15) it and `tools/convert-to-3.js` write through `tools/lib/safe-output.js`: `--out` must not exist and must not be inside an input (after resolving links); everything is written into `<out>.partial-<pid>-<hex>` (holding `INCOMPLETE.txt` while written), read back byte for byte and verified, then renamed; any failure removes it. Files are read strictly as UTF-8 (BOM kept, as the app does); not UTF-8, or a Slaughter Cataloger CSV the reader refuses, stops the run. `change-titleid.js` reads header-only files as the app does (`allowEmpty`, DF-21): a valid empty file of the library is carried into the output byte for byte, renamed with its title's files; a header-only file the reader refuses (a header row that is not exactly 3.0's, not UTF-8, no bytes) stops it; one the app does not take in (another library's name, a second Titles file) is an uncarried item. It refuses to rename a file onto a name the folder already holds (compared ignoring case). `change-titleid.js` refuses a library with `_issues/` (always) and, unless `--partial-copy`, a folder holding anything besides its loaded catalog CSVs (other files, subfolders, links, CSVs the reader skips), listing each; `--partial-copy` lists them in its report and in `PARTIAL-COPY.md` in the output. It also refuses unless every file holding no record of the title would be written back byte for byte. `convert-to-3.js` lists everything it did not convert, on screen and in each `CONVERSION-REPORT.md`. `SC_TEST_FAULT` (tests only) makes a run fail on purpose: `throw-after-write:N`, `kill-after-write:N`, `verify`, `before-rename`. Exit status for both: 0 done, 1 refused or not verified (nothing written), 2 usage.
- Duplicate or missing Entry Order in a file → row order decides. Speculative/N/A lists also accept internal field keys (e.g. `firstYear`).
- Speculative / N/A lists use canonical CSV header names (2.x label variants mapped via `labelAliases`, unknown names kept).
- Issues inherit 12 title-level fields (`schema.INHERIT`). Issue record holds a value only for overridden fields (`overrides`); CSV writes effective values + `Overridden Fields`. On load: override if listed, N/A, or non-blank and different from the title. **One rule decides inheritance everywhere** (`records.inherits`, used by `effective`, `catalog.issueView` and the issue form): a field is inherited only when the issue does not override it AND holds no value of its own — so an issue read while its title was missing never has its values replaced by the title's when the title is added later (independent check round 3, B). Own values are compared trimmed, as on load. Adding a title in Library also settles such issues in the same undo step (`records.settleIssues`, the load rule: differing values become overrides, equal ones inherited), so the session, the saved files and a reload agree, and a new issue drafted from one carries its overrides (round 4). A ? the issue puts on a value it inherits stays in the view and every output (`catalog.issueView`; round 4 — such marks were being dropped).
- Contents get permanent `ContentID` (`TitleID-C` + 6 chars) and `Parent ContentID` (resolved from Parent Item text: same issue, title match, nearest earlier on ties).
- Formula guard (exactly reversible): a value matching `^'*[=+\-@\t\r]` is written with one more leading `'`; reading removes one `'` from a value matching `^'+[=+\-@\t\r]`. `"-- END"` ↔ `'-- END`, `"'-ism"` ↔ `''-ism`. Existing data had one guarded cell (`'-- END`), which reads the same under both rules.
- BibTeX: TeX specials escaped incl. `< > \``, ligatures broken (`-{}-`, `'{}'`), titles/journal double-braced to keep capitals, corporate names or names containing "and" braced as one author, page ranges keep `--`. Checked by Better BibTeX's parser and citation-js (`tools/test-formats.js`).
- Several files with overlapping IDs in a folder → newest loaded, others reported. One Titles file per library. Files from another library slug are skipped.
- **Empty files (DF-19, A2 repair).** Deleting the last record of a file saves it as its header row only. `records.readFile(name, text, { allowEmpty: true })` reads such a file as an empty file of its kind (`empty: true`, no records) only when its header row is exactly that of one kind as the writer writes it: every 3.0 heading in order, then extra columns that are no heading or alias of any kind; anything else stays refused ("No data rows." …). The app asks (opening a folder, loading files, reading the folder again on reconnecting: `session.js`), and so does `change-titleid.js` since DF-21 (the rule in its paragraph above: a valid empty file is carried byte for byte); `convert-to-3.js` does not, so for it a header-only file is still "No data rows." and is listed as not converted. `buildLibrary` takes an empty file in only under this library's names (`SCAT_<slug>_…`) once files with rows have named the library, never lets an empty Titles or Authorities file stand in for one with rows (an empty file sorts after one with rows), and notes each one ("No rows yet: an empty … file"). The Titles header row is the same in 2.0 and 3.0, so an empty Titles file's version cannot be told; those rules decide.
- **The library's only title cannot be deleted** (DF-19): the library's slug, name and note live in the rows of the Titles file. The title page shows Delete title off, with the reason (`#last-title-note`); and save never writes a Titles file with no title (Undo of a new library's only title, say): that file stays changed and the message says why.
- Save backs up the disk copy the first time a file is overwritten in a session (and again if it changed on disk). **A backup is never written over** (second review, F2-01): each session gets its own folder `_backups/<date-time>-<8 hex random>` (made only if the name is free, else `-2`…), a name already taken inside it gets `-2`…, each copy is read back and compared before the live file is replaced (else the save of that file fails with the reason), and `BACKUPS.txt` lists every copy (time, copy, original, why). Copies are the file's **bytes** (`arrayBuffer`), checked byte for byte; a copy that fails or doesn't check is removed again (its name was free). The backup folder is tied to the library folder handle and looked for again on every save (deleted → a new one, files copied afresh). `tools/test-backups.js` (Node, in-memory folder holding bytes, frozen clock, forced random clashes).
- **Reading files** (`storage.js` `contentOf`): bytes, decoded as strict UTF-8 with the BOM kept as the first character (csv.js notes it and writes it back, so saves keep it). A file that is not valid UTF-8 (a spreadsheet's plain "CSV" in a Windows code page) is not guessed at: `encodingError` → `records.readFile` refuses it with the reason; its text is the raw bytes one char each, so its fingerprint still changes when it does and it counts as unloaded (never written over).
- Saving refuses while the folder is being read or checked (`ui.busy`); opening, closing, switching or reconnecting a folder waits for a running save (`waitForSave`).
- TitleID is fixed once a title exists (Title Code read-only, First Year value locked; ? still allowed).
- The Library list sorted by status follows the order of the work (`CATALOGING_STATUS`: Not started … Fully cataloged, On hold); a title with none counts as Not started, as it is shown; a status not in the list goes last (A2 minor; before, alphabetical).

## Stage 2 (Issues) — `js/ui/issues.js`
- No issue selected → overview table (with gap rows and the Roman short-name fix offer). Issue selected → run list (left) + issue form. `#/issues/<tid>/new` → a draft.
- A draft follows a base issue: sticky fields and the base's overrides/N/A are carried; numbers and date move on (`numbering.nextIssue`) from the last *regular* issue (not supplement/special) at or before the base; date step = cadence inferred from the last two regular issues unless chosen. Advance choices are remembered per title in localStorage (`sc3.advance.<tid>`, a convenience only). Drafts live in memory per title for the session; they are never records and never stored (not in the working copy, not in localStorage). **A changed draft is protected (K-D1):** `SC.drafts.changed()` (issues.js) lists the titles whose draft the person has changed (`touched`: a value, a ? or N/A, Start next volume) and which now differs from the draft `makeDraft` would make afresh for the same base and settings; a draft only opened, ready after Record, changed back, or changed only in its "Moves on" settings is not listed. Leaving the page (`beforeunload`, app.js) asks while one is listed; `confirmDiscard` (session.js) puts files and drafts in one question (the files-only wording is unchanged; drafts alone: "The new issue being entered for X has not been recorded. Continue without recording it?"). When another library replaces this one or it is closed (`openFolder`, `loadFiles`, `newLibrary`, `closeLibrary`, after that question), every draft is discarded (`SC.drafts.discard()`), so the library opened next starts with fresh drafts; restoring, reconnecting and folder syncs keep them. Start over and Follows keep their own question for a touched draft; declined, the Follows list shows again the issue the draft still follows (`rebase` returns false and the select is put back; before, it kept showing the one chosen).
- Short name: follows the previous issue's pattern (`nextShortName`), Roman numerals that touch a letter get separated ("VXIIIN2" → "V.XIII N3"); typing your own stops it following. `fixShortName` powers the one-click, undoable rewrite of old run-together names.
- Record (Ctrl/⌘+Enter) never asks: unaddressed count is shown (click = go to first), duplicates are pointed out. IssueID minted at record time; a new issue after a mid-run base shifts later Entry Orders.
- **A run in several Issues files** (made outside the app; the app itself keeps one Issues file per title). The run is shown file by file, Entry Order within each file; which file comes first is taken from the files' names (`store.indexes`, default-locale collation as `localeCompare`; search's catalog order uses the same collator), never from the order the folder lists them. Entry Order is per file and the schema records no order between files, so the order between them is name-derived: `…_ISSUES_2.csv` sorts before `…_ISSUES.csv`. Making it independent of names would change the multi-file ordering contract: registered as **DF-22**, the name order kept provisionally; options B, C, D and F of the DF-20 checkpoint's `ordering-decision.md` are deferred to Stage B (import planning). **The Library page names every such title** (option E, DF-22 batch): `SplitRuns` in `js/ui/library.js` lists each title whose run is in more than one Issues file, its files in exactly the order the run is shown (taken from `store.issuesOfTitle`) with the issues each holds, says that the order comes from the names and may not be the order of publication and that nothing was changed, and how to change it (rename the files to sort in run order, `…_ISSUES_01.csv`…, and open the library again). A status message, not a dialog: nothing waits for it. It is worked out from the records on every render (titles in catalog order), so it is the same after a reload or a fresh open, in folder or files mode, and follows every change; it is not part of the load report, and nothing is reordered, merged, renamed or written. A file holding all of two titles' issues, or an emptied (header-only) Issues file beside a run, splits nothing. **A new issue goes into the file of the issue it follows**, right after it; only the later issues of that file move down (DF-20, A2 repair). With nothing to follow (a title's first issue, or a draft whose issue was undone), it goes at the end of the run: the file of the run's last issue, else `fileForNew` (the title's file for new issues). For a run in one file this is exactly what it was.
- Gaps: `gapBetween` + `numbersHeld` — numbers missing between consecutive regular issues that the run holds nowhere; each reported once.
- Run list shows short names without the words every short name shares (`sharedStart`), keeping "No."/"Vol.".

## Stage 3 (Contents) — `js/ui/contents.js`
- One grid per issue in Sequence order; nesting = depth from Parent ContentID (`toc.depths`). Sequence kept 1..n on add/move/delete (all real data was already clean 1..n).
- **Structure follows the Parent ContentID links, not the indentation (D-12, A3 batch 2).** A part need not follow its parent directly: real issues have a parent's parts on both sides of an unrelated item (the twin: item 3 has parts 4, 6 and 7; item 5 is top level). Such a part is *detached* (`toc.detached`: its parent is not the nearest less-indented row above it). An item's *block* is the item and the contiguous run of its own descendants right after it (`toc.blockEnd`); its *descendants* are all of them, wherever they are (`toc.descendants`). Delete removes the item and its descendants (the question counts them and says how many are further down). Move swaps the item's block with a true sibling's block next to it (same parent), and is refused (a silent no-op, as before) if no sibling is there or any part would come before its parent (`toc.validOrder`). Nest makes the item a part of the previous true sibling whose block ends right above it. Un-nest moves the item to its grandparent; a following sibling inside the parent's own contiguous block is adopted (as before, so the list still reads in order), but a detached item adopts nothing. Insert below opens the row after the item's block; a new row's parent is the row above or one of its ancestors (`toc.parentFor`), never an unrelated item. On lists where every part follows its parent (every sample issue) all of this gives exactly what the earlier depth-based code gave: `tools/lib/toc-contiguous-reference.js` keeps that code for `tools/test-hierarchy.js` to compare with. The grid marks a detached part (a dashed rule; "part of no. 3, “Title”, above", tied to the title cell by `aria-describedby`) and its parent ("its parts nos. 6, 7 are further down"). The view model sets `partOf` on a detached item; Catalog and WordPress (when nested items are shown) say "part of “Title”" (or "part of item N" with no title), the proofing sheet "part of “Title” (no. N, above)"; RIS and BibTeX already said "Part of: Title".
- Draft rows (the end row, an inserted row) share the item row's shape and key, so the first value typed turns them into an item without losing the cursor; their ContentID is minted up front.
- Cells and form fields commit only what was typed (a `typed` ref); otherwise they show the record's value. This prevents a stale empty value overwriting a value set from outside (paste, undo). **When the record's value changes from outside while the field holds typing that leaves it as it was** (typed and deleted, or taken back with the browser's own undo), the typing is dropped (`seen` ref in `Field`, kit.js, and `Cell`, contents.js): the field shows the new value and leaving it writes nothing. Before, it kept the old text and wrote it back, reversing an Undo and losing Redo (D-K1, A2 keyboard batch). Typing that differs from the record still wins.
- **Keys** (`app.js`): Ctrl/⌘+Z undoes, Ctrl/⌘+Shift+Z and Ctrl/⌘+Y redo, the library's, unless the focus is in a text box that is not a field (search, filters) or a field holding typing that differs from its record (`data-pending`): then the browser's own text undo. Ctrl/⌘+S saves when anything is unsaved. **Leaving the page** (`beforeunload`) asks while files are unsaved or a field is `data-pending` (D-K2: such typing is in no working copy); the working copy brings unsaved files back after a reload, but the undo history starts afresh. Close library and Open another folder ask "N file(s) have unsaved changes. Continue without saving them?" before discarding (`confirmDiscard`, which also guards Load CSV files and Start a new library; those are offered only on the welcome page, where nothing is open); Choose folder keeps the work. In-app navigation commits what is typed (the field is left) and asks nothing: the store keeps everything. An unrecorded issue draft is kept in memory for the session only; since K-D1 a changed one is asked about before it is lost (Stage 2 rules). Alt+Page Up/Down keeps the place: the same field id (`f-<key>`) of the next issue, or the same column of its first item in the grid; from outside a field, no field takes the focus.
- **Accessibility (A6)** (`tools/test-accessibility.js`): text meets 4.5:1 (`--ink-3` is the lightest text grey; no opacity on text, placeholders included); every view has one `h1` (a visually hidden `.vh` one where the entry card is the visible heading); every control is a button, link or field (sortable headings hold a `button.sort`; a table row's first cell is a link, the row's own click is for the mouse only; Load CSV files is a button that opens the hidden file input); a long run of links is one Tab stop, moved along with the arrow keys, Home and End (`rovingKeys` in kit.js: the run beside an issue, the strip, the Names list); the heights of the bars that stay in view are measured as they wrap (app.js sets `--top-h`, `--stick`, `--stick-pad`, `--stick-foot`), so each sits under the one above and `scroll-padding` keeps a field reached with Tab clear of them; in a window under 500 px tall nothing stays in view; a focused text box in a `.field` is marked whatever its state; Alt+Shift+Delete deletes a Contents item; a form that replaces the button that opened it takes the focus (and Cancel gives it back).
- Author/Type: spreadsheet-style inline completion (most used, this title's first). Text cells wrap (`field-sizing: content`); Notes fold to one line until focused.
- Paste of several lines / tabbed columns → items (`toc.parseLines`). Top-level items get Parent Item in N/A Fields (as in all converted data).
- Contents whose issue is in no Issues file are listed in the issue picker; their titles appear in the context bar.

## Library › Names — `js/ui/names.js`
- Route `#/names[/<AuthorityID or k:<key>>]`, shown as a tab of Library (rail highlights Library). List (filters All / Headings / No heading / Needs review / Suggested matches, search; first 600 shown) beside a detail pane: a heading (fields, forms with Remove, "Possibly the same name" incl. the bare surname, find a form to add, credits linked to their contents) or a name without one (Make heading with the suggestion editable, Combine with its likely group, Add to a heading). ## Run strips — `js/ui/strip.js`

## Stage 4 (Compiler) — `js/ui/compiler.js`
- No context bar: the stage has its own title list (tick one or several; starts with the route's title). Output, options and selection are remembered in localStorage (`sc3.compiler`, a convenience only). One title → choose some volumes/years (`catalog.scopeGroups`).
- A TitleID in the address (`#/compiler/<tid>`) chooses that title when the Compiler opens and whenever the address changes to another title while it is open (DF-17); ticking titles leaves the address as it is.
- Preview is built from the view model with `limit` 25 issues per title, divided among the titles when several are chosen (at least one each; A4: 25 each made the preview the whole library, and a 1,000-issue proofing catalog froze the page for over five seconds) (HTML outputs in a sandboxed iframe, text in a `<pre>`); Download / Copy / Open (blob URL, for printing) build the whole output. The Compiler is the only export besides saving CSVs, and it never writes to the library folder.
- Catalog/WordPress default to top-level items only (2.7's "hide nested" default); proofing, RIS and BibTeX include nested items. Catalog shows an issue's place/publisher/editors/subtitle only where they differ from the title; the Type column only for titles that record types.
- Proofing: explainer → per title a title proof sheet → every issue on its own printed pages (`break-before: page`), every schema field listed (a unit test enforces this), status ?/[N/A]/[blank]/from title; an item and its note are kept together (`tbody.item`).
- RIS/BibTeX: one record per contents item; plain values, speculative fields named in a note; TitleID/IssueID/ContentID carried (BibTeX key = ContentID). Authors are their heading where one exists (option, default on), else the credit without a role; "Credited as:" note when they differ.
- Name index (`names`): web page / Markdown / text; entries = headings, or for unheaded names the suggested heading (or as credited); forms each was credited under; see-references from forms that file under another first word; credits as "Vol. 1, no. 1 (whole no. 1), May 4, 1872, p. 1: “Title” (role)".

## Issue packages — `docs/ISSUE-PACKAGE.md` (format `slaughter-cataloger-issue` 1.0)
- One package = one issue's text, item segments, mentions, cover, source, provenance and publication decisions, beside the catalog, never instead of it. Candidate Contents rows (`items.json`) use the exact 3.0 headers; the CSV schema does not change. Installed later under `<library>/_issues/<TitleID>/<IssueID>/` (the 3.0 reader only reads top-level `*.csv`).
- `js/core/issuepkg.js` (pure; tools only for now): `validate(files, {sha256})` → `{ok, errors, warnings, pkg, summary}`, every error with a code (spec §14); `parseJSON` (no BOM, valid UTF-8, no duplicate keys, no unpaired surrogates); `serialize` (2-space + newline; parse→serialize is byte-identical); `cpIndex/cpLength/cpSlice` (**offsets are code points**; never slice page text with JS indexes); `spanText/segmentText/itemParts/itemText/transcription`; `scanMarkup` (the closed markup set, §6); `inventoryHash`. Unknown fields are kept and warned; `origin` (keyed by source file) carries converted data 1.0 has no field for.
- `js/core/zipread.js` (pure; inflate injected): refuses unsafe/colliding names, links, special files, encryption, ZIP64, prepended/overlapping/trailing data, lying sizes, CRC errors, size/ratio over limits. `checkPath`/`checkNames` are shared with folder reading (`tools/lib/package-io.js`, which also writes new folders via a temporary sibling + rename, never over an existing one).
- `tools/lib/staging.js` + `tools/convert-staging.js`: the ingestion process's provisional `draft-0.1` layout → native. Only reads the staging package; keeps every staging file byte for byte (`provenance/staging/…`, or as the native cover/source); keeps identifiers (IssueIDs, local item keys, segment/span ids, package id); never mints ContentIDs; never carries an approval; drops only derived text copies after checking them equal; `reconstruct()` rebuilds `fulltext.json`, the candidate rows and the deep index exactly from the native files, and `convert()` refuses to return unless they match. `tools/validate-issue.js` checks any package (and recognises a staging one).
- **Format 1.0 is frozen** (2026-10-14, after review; spec §17). Any change is a new version under spec §2. Amended the same day, before freezing: pages are **logical pages in reading order**; optional `locations` per page (`source`, `pdf_page`, `region` full/left/right/top/bottom, `rotation` 0/90/180/270 clockwise to read upright, optional `size` + `box` in upright points, origin top left, y down; `uprightToPDF`/`pdfToUpright`/`storedRect`). Locations on all pages or none; none = page N is all of PDF page N. Overlaps are checked in stored (unrotated) terms; unused PDF pages warn. `folio_status` adds `unverified`. `identity.status` `resolved` (default) / `title-resolved` / `unresolved`: unresolved IDs are `null` in identity and empty in rows, `provisional_key` required, anything catalog-shaped (`isCatalogShaped`, any case) refused as a placeholder, `installed` needs `resolved`. `identity_history` entries are typed: `kind` `issue_id` (default; `id`, `superseded`) or `provisional_key` (`key`, `retired`). `<!-- LOGICAL_PAGE_N_START/END -->` anchors are checked; `PDF_PAGE: N` must be one of the page's PDF pages. Editorial-looking brackets outside `[supplied: …]`/`[unclear: …]`/`[illegible]` are always a `markup` warning (escape a printed one: `\[Note: …\]`); each must be reviewed by a person before any full-text public export is approved. `cover.location` (code `cover`).
- Only `draft-0.1` staging converts. Another layout (e.g. one declaring `manifest_schema`) is refused **by name** by the converter and named by `validate-issue.js`; a second converter is a separate decision, not part of 1.0. Real staging packages stay outside the repository.
- Tests: `tools/test-issuepkg.js` (twin, booklet, every rejection, conversion, ZIP and CLI paths, coordinate mapping, regression cases T1–T17 of spec §17, Python cross-check via `tools/check-offsets.py`; `--private <real package>` for the private acceptance run, counts only). Test archives come from `tools/lib/zip-maker.js` (tests only).

## Search — `docs/SEARCH.md` (Phase 2)
- `js/core/search.js` (pure; `SC.search`): `fold`/`tokens`/`foldMapped` (NFD minus U+0300–036F, lower case, æ œ ß ø ł đ ð þ ı ς table, apostrophes removed, a period between single letters removed, other runs → one space; an ASCII fast path tested equal to the full scan), documents per title / issue (own values only: `records.inherits` decides; numbering as "vol N no N whole no N") / item (credits also by `names.nameKey`) / name (from `nameIndex`, a one-pass equivalent of `names.index`, tested entry for entry), `parse` (words, last word ≥ 2 chars a prefix, phrases, `title: credit: type: year: id: note: in:`, `-` exclusion, ID-shaped words, 200 chars / 32 terms, notices; never throws), `createIndex(getState)` → `ensure/update(changed)/reset/run(q, {order, expand})/stats/dump`, `highlight`/`snippet` (marks the original text). Ranking: tier (exact ID 1, direct 2, heading expansion 3), then Σ weight × quality (whole word 1, prefix 0.6, first word ×1.5, whole field 3), then catalog order. Field lists name schema keys and the module throws if one is missing.
- **Index:** in memory only, lazy (built on the first focus of the box or the first `#/search`; nothing at start-up), kept up from store events (`change` → the changed records' documents, a title also its issues; a credit or heading change → names re-worked out, only changed entries re-indexed; `load` → reset). The 500-step property test keeps it equal to a fresh build.
- `js/ui/search.js`: `SearchBox` (top bar, not on the search page; adds `from=<tid>` from Issues/Contents) and `SearchPanel` (scope line naming the library; groups Titles, Issues, Contents, Names as `section`+`h2`+`ol`; chips `kind=`; Best match / Catalog order `order=` (items then under an `h3` per title › issue, each labelling its `ol`); a summary naming the empty kinds too; Show more +200 focusing the first new row; "Only in <title>" offered, never applied; a polite status that speaks only when the query, kind or order change, never for live updates; Back restores focus and rows from memory). `/` focuses the box when not typing. Contents arrival: row centred, marked (`arrived`, `aria-current`), focus on its Item Title cell; nothing committed.
- **Read-only:** no store mutator, storage, `innerHTML` or issue-package reference in either module (a static test); nothing under `_issues/` is opened (browser canary test with the twin placed in the test folder).
- **Performance** (accepted 2026-10-15, Phase 2 closeout; `docs/SEARCH.md` §10): first-use indexing and every search interaction within **2,000 ms** on the generated 10,000-item library (`tools/lib/search-library.js`). This is the only performance check that fails: in Node, the cold first build (median of 5 fresh processes), the full build, every query, the first query after an edit, updates and the names rebuild; in Chromium, focus to index ready, the results page and typing, at both scales. The Phase 2 budgets (first build 300 ms on a mid-range laptop, full build 300, query p95 50, update 5, names 100, render 100, typing 250) are **diagnostic targets**: printed as met or NOT MET, never a failure. `SC_PERF_SUMMARY` (set by `run-tests.sh`) collects the figures for the run's summary and the GitHub job summary. `SC_SEARCH_TIMES=<file>` writes every time. `SC_BUDGET_MODE` is retired: a notice, no effect.
- **Known, not changed in Phase 2:** `names.index` is O(headings × forms), about 0.6 s at 2,000 headings and 10,000 items, which the Names tab pays; search does not use it. A future optimization candidate.

## Design
Catalog-card look: cool paper `#EEF1F3`, ink `#1B2430`, ribbon blue `#1F5FA8` for entered values, ochre for speculative, archival red only for unsaved.
